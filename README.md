# ВышКат — учёт парка кикшеринга
Консольное приложение на C# (.NET 10) для учёта парка сервиса «ВышКат»: приём транспорта через техосмотр, учёт вещей на балансе, отчёты по числу единиц и расходу энергии, список транспорта для новичков и инвентарный список

## Логика решений

### Структура проекта

```
src/VyshKat.Core/         модель (Domain/) и логика (Services/)
src/VyshKat.ConsoleApp/   меню, ввод-вывод, настройка DI-контейнера
tests/VyshKat.Tests/      юнит-тесты
```

Логика отделена от консоли (`VyshKat.Core` ничего не знает о вводе и выводе, поэтому её можно проверять тестами)

### Модель

Интерфейсы:
- `IInventoryItem` — объект на балансе: инвентарный номер и название;
- `IEnergyConsumer` — объект, который потребляет энергию: суточный расход в кВт*ч.

Классы:

| Класс | Представляет | Потребление энергии |
|---|---|---|
| `Vehicle` | базовый класс транспорта, хранит простоту для новичка | - |
| `Bicycle` | велосипед | - |
| `ElectricScooter` | электросамокат | + |
| `ElectricBike` | электровелосипед | + |
| `Equipment` | базовый класс вещей | - |
| `Helmet` | шлем | - |
| `Station` | станция | + |
| `ChargingCabinet` | шкаф подзарядки | + |

Почему так:
- Интерфейсы разделены, потому что не всё, что стоит на балансе, тратит энергию

- Некорректный объект нельзя создать (конструкторы проверяют данные и выбрасывают исключение)

### Сервисы

| Класс | Реализует |
|---|---|
| `IServiceCenter`, `ServiceCenter` | техосмотр, который отклоняет электротранспорт с расходом больше 2 кВт*ч в сутки (признак неисправного аккумулятора) |
| `Park` | хранит всё, что стоит на балансе (не допускает повторных инвентарных номеров) |
| `ParkService` | принимает в парк: транспорт только после техосмотра, вещи сразу |
| `ParkReports` | отчёты (число единиц, суммарный расход энергии, транспорт для новичков, инвентарный список) |

### DI-контейнер

Зависимости настраиваются в `Program.cs` через `Microsoft.Extensions.DependencyInjection`. Классы не создают зависимости сами, а получают их через конструктор: например, `ParkService` получает `IServiceCenter` и `Park`. Все сервисы зарегистрированы как `Singleton`, чтобы `ParkService` и `ParkReports` работали с одним и тем же парком

## Запуск
```
dotnet build                                  # собрать проект
dotnet run --project src/VyshKat.ConsoleApp   # запустить приложение
dotnet test                                   # запустить тесты
```

После запуска появляется меню:

| Пункт | Выполняет |
|---|---|
| 1 | принять транспорт (с техосмотром) |
| 2 | поставить вещь на баланс |
| 3 | отчёт: число единиц и суммарный расход энергии |
| 4 | список транспорта для новичков |
| 5 | инвентарный список: номера и названия всей техники и вещей |
| 6 | загрузить технику и вещи из файла |
| 0 | выход |

**Загрузка из файла (пункт 6).** В корне репозитория лежит файл `demo-data.csv` с примерами. Программа спрашивает путь к файлу, загружает строки по одной и для каждой пишет результат: принято, отклонено техосмотром или ошибка. В примере есть все случаи: обычный приём, отказ техосмотра, повторный инвентарный номер, ошибка формата, вещи с расходом энергии и без

Формат строки: `вид;инвентарный номер;название;простота;расход кВт*ч`. Виды: `bicycle`, `scooter`, `ebike`, `helmet`, `station`, `cabinet`

Демонстрационные данные лежат в файле, а не в коде, поэтому можно загрузить свой файл с другими данными

Если ввести что-то неправильное (буквы вместо числа, число вне диапазона, пустую строку), программа не завершается с ошибкой, а просит ввести значение заново

## Ответы на обязательные вопросы

### 1. Какой принцип SOLID применён наиболее явно и где?
**Принцип инверсии зависимостей (D)**

`ParkService` (файл `src/VyshKat.Core/Services/ParkService.cs`) зависит не от конкретного класса техосмотра `ServiceCenter`, а от интерфейса `IServiceCenter` и получает его через конструктор:

    public ParkService(IServiceCenter serviceCenter, Park park)

`ParkService` не знает, какой именно техосмотр ему передали. Конкретная реализация выбирается в одном месте — при настройке DI-контейнера в `src/VyshKat.ConsoleApp/Program.cs`:

    services.AddSingleton<IServiceCenter, ServiceCenter>();

Что это даёт:
- правила техосмотра можно поменять, не трогая логику приёма в `ParkService`
- в тестах вместо настоящего техосмотра подставляется фейковый `FakeServiceCenter`, и логику приёма можно проверить отдельно от правил техосмотра (`DependencyInjectionTests`).

### 2. Какой принцип сознательно ограничен и почему это приемлемо?

**Принцип открытости/закрытости (O)**

Модель и сервисы закрыты для изменений: новый вид транспорта (например, моноколесо) добавляется новым классом-наследником `Vehicle`, и `ParkService`, `ParkReports`, `ServiceCenter` менять не нужно

Но в консольном приложении виды перечислены явно:
- в `ConsoleMenu.AcceptVehicle` и `ConsoleMenu.RegisterEquipment` — `switch`, который по номеру из меню создаёт нужный класс
- в `FileImporter.ImportLine` — `switch`, который по виду из файла создаёт нужный класс
- в `DisplayNames.KindOf` — названия видов для вывода

Поэтому новый вид потребует дописать по строке в эти два места

Почему это приемлемо:
- меню всё равно должно знать, какие виды показать пользователю и какие данные у него спросить
- изменения затрагивают только консоль, а логика в `VyshKat.Core` остаётся нетронутой
- чтобы обойтись совсем без правок, понадобилась бы фабрика или автоматический поиск всех видов транспорта — для трёх видов это было бы усложнением без пользы

### 3. Что сломается (или не сломается) при расширении программы?

**Новый вид транспорта (моноколесо)**
- Добавляется класс `Monowheel : Vehicle, IEnergyConsumer` в папке `Domain/`
- Не меняются: `ParkService`, `ParkReports`, `ServiceCenter`, `Park`. Моноколесо само попадёт в подсчёт энергии, в список для новичков и пройдёт техосмотр, потому что эти классы работают с `Vehicle` и `IEnergyConsumer`, а не с конкретными видами
- Меняется только консольный слой: `ConsoleMenu`, `FileImporter` и `DisplayNames`. Если название в `DisplayNames` забыть, программа не сломается — выведется имя класса

**Сотрудник службы эксплуатации**
- Добавляется класс `Employee`, который **не** реализует `IInventoryItem`, потому что сотрудники по условию не ставятся на баланс
- Ничего не ломается: сотрудник не попадает ни в `Park`, ни в отчёты, а модель техники и вещей не меняется
- Именно поэтому инвентарный номер задан интерфейсом `IInventoryItem`, а не общим базовым классом: иначе сотрудник получил бы номер поневоле

**Склад запчастей**
- Запчасть, которую нужно учитывать на балансе, — это новый класс-наследник `Equipment` (например, `SparePart`). Он сразу появится в инвентарном списке и в отчёте о числе вещей
- Если складу нужна своя логика (остатки, списание), она выносится в отдельный сервис, например `WarehouseService`, рядом с `ParkService`. Существующие классы не меняются

### 4. Какой тест фиксирует решение техосмотра и правило «для новичков»? Как подменяется зависимость?

**Решение техосмотра**

- `ServiceCenterTests` — проверяют правила настоящего техосмотра:
  - `Inspect_Bicycle_Approves` — велосипед принимается
  - `Inspect_EnergyAtLimit_Approves` — расход ровно 2 кВт*ч принимается
  - `Inspect_EnergyAboveLimit_RejectsWithReason` — расход выше 2 кВт*ч отклоняется, и указана причина
- `ParkServiceTests` — проверяют, что приём слушается решения техосмотра:
  - `AcceptVehicle_WhenInspectionRejects_VehicleIsNotAdded` — отклонённый транспорт не попадает в парк
  - `AcceptVehicle_WhenInspectionApproves_VehicleIsAdded` — одобренный попадает
  - `RegisterEquipment_AddsWithoutInspection` — вещи принимаются без техосмотра

**Правило «для новичков»**

- `VehicleTests.IsBeginnerFriendly_DependsOnSimplicityThreshold` — проверяет простоту 1, 5, 6 и 10, то есть границу между 5 и 6
- `ParkReportsTests.GetBeginnerFriendlyVehicles_ReturnsOnlyVehiclesWithSimplicityFromThreshold` — в список для новичков попадает только подходящий транспорт, а вещи не попадают

**Как подменяется зависимость**

Вместо настоящего `ServiceCenter` используется `FakeServiceCenter`. Он реализует тот же интерфейс `IServiceCenter`, всегда возвращает заранее заданный ответ (принять или отклонить) и запоминает, какой транспорт ему передали

Подмена сделана двумя способами:
1. **Через конструктор** — в `ParkServiceTests` фейк передаётся в `new ParkService(fake, park)` вместо настоящего техосмотра
2. **Через DI-контейнер** — в `DependencyInjectionTests.Container_WithFakeServiceCenter_ParkServiceUsesFake` фейк регистрируется в контейнере вместо `ServiceCenter`. Фейк отклоняет обычный велосипед, который настоящий техосмотр принял бы. Значит, `ParkService`, созданный контейнером, действительно получил фейк

### 5. Что сделал ИИ?

ИИ-ассистент использовался как учебный помощник: до этого задания я писала в основном на C++, и опыт работы с C# был относительно небольшим

**Изучение C# -** поиск отличий C# от C++ и обучение програмированию на С#:
- **классы и память:** интерфейсы вместо классов с чисто виртуальными функциями; один базовый класс плюс любое число интерфейсов; `abstract`, `sealed`, вызов базового конструктора через `base(...)`; сборщик мусора вместо `delete` и умных указателей; `List<T>` и `IReadOnlyList<T>` вместо `std::vector` и `const&`
- **синтаксис:** свойства (`{ get; }`, `=>`) вместо геттеров; `record`; `var`, `foreach`; `??` для проверки на `null`; интерполяция и форматирование строк; `TryParse` с `out`; `using var` как аналог RAII; программа без `Main`
- **работа с коллекциями и типами:** LINQ (`OfType`, `Where`, `Sum`, `Any`, `Select`) вместо циклов и `<algorithm>`; лямбды; проверка типа `is` вместо `dynamic_cast`; switch-выражения
- **исключения и тесты:** исключения и фильтры `catch ... when`; атрибуты и проверки xUnit

**Работа с .NET SDK 10 -** помощь с установкой необходимых расширений и объяснение того, как собирать и запускать проект и тесты

## Принципы SOLID

| Принцип | Приминение |
|---|---|
| **S** — единственная ответственность | У каждого класса одна задача: `ServiceCenter` проверяет транспорт, `Park` хранит, `ParkService` принимает в парк, `ParkReports` считает отчёты, `ConsoleMenu` общается с пользователем |
| **O** — открытость/закрытость | Новый вид транспорта или вещи добавляется новым классом-наследником `Vehicle` или `Equipment`, без изменений в `ParkService` и `ParkReports` |
| **L** — подстановка Лисков | Любого наследника можно использовать вместо базового типа: например, `ParkReports` суммирует расход всех `IEnergyConsumer`, не разбираясь, самокат это или станция |
| **I** — разделение интерфейсов | `IInventoryItem` и `IEnergyConsumer` разделены, поэтому велосипед и шлем не обязаны иметь расход энергии |
| **D** — инверсия зависимостей | `ParkService` зависит от интерфейса `IServiceCenter`, а не от `ServiceCenter` (реализация выбирается в `Program.cs`, в тестах подменяется фейком) |
